# RelayDesk 제품 목표 명세

## 1. 한 문장 목표

> RelayDesk는 글로벌 B2B IT 기업이 고객의 기술적 문제를 더 빠르고 정확하게 이해하고, 필요한 팀까지 연결해 해결하도록 돕는 고객 대화 기반 기술지원 워크스페이스다.

1차 프로토타입은 채팅 기능의 폭을 넓히는 대신, **기술적 맥락을 갖춘 문의가 지원 담당자의 판단과 처리 품질을 높이는가**를 검증한다.

---

## 2. 소크라틱 질문으로 정의한 문제

### Q1. 왜 일반 고객 채팅으로는 충분하지 않은가?

글로벌 IT 제품의 문의는 단순한 응대가 아니라 기술 문제를 파악하고 조사하는 일이다. 고객 이름과 이전 대화만으로는 다음 질문에 답할 수 없다.

- 어느 Organization과 Workspace에서 발생했는가?
- 어떤 제품·버전·환경·리전에서 재현되는가?
- 오류 코드, Request ID, 로그, 최근 배포는 무엇인가?
- 단일 고객 문제인가, 여러 고객에게 영향을 주는 Incident인가?

따라서 문제의 본질은 "메시지가 부족하다"가 아니라 **문제를 판단할 맥락이 대화에서 분리되어 있다**는 데 있다.

### Q2. 고객이 처음부터 완벽한 기술 정보를 제공할 수 있는가?

항상 그렇지 않다. 고객은 채팅이라는 쉬운 방식으로 도움을 요청해야 한다. 다만 Technical issue를 선택했을 때는 제품, 환경, 오류, 재현 절차, 첨부파일을 단계적으로 제공할 수 있어야 한다.

그러므로 RelayDesk는 고객에게 티켓 작성을 강제하지 않고, **쉬운 대화를 구조화된 지원 정보로 발전시키는 경험**을 제공한다.

### Q3. 지원 담당자가 가장 먼저 알아야 하는 것은 무엇인가?

답변 문구보다 먼저 고객의 영향도와 기술 환경을 알아야 한다. Enterprise 고객의 Production 환경에서 발생한 EU-West API 502 오류는 일반 사용법 문의와 동일한 방식으로 처리해서는 안 된다.

그러므로 운영자 화면의 중심은 메시지 목록이 아니라, 다음을 함께 보여 주는 Context Panel이다.

- 고객·Organization·요금제
- 제품·버전·환경·리전
- 오류 정보·로그·최근 배포
- 이전 유사 문의·현재 서비스 상태
- 연결된 Case·Incident·Engineering Issue

### Q4. 모든 대화를 즉시 개발 이슈로 만들어야 하는가?

아니다. 간단한 질문은 대화에서 해결하고, 조사가 필요한 문제만 Support Case로 전환하며, 제품 변경이나 버그 수정이 필요한 경우에만 Engineering Issue로 연결한다.

```text
Conversation
  └─ 조사와 추적이 필요할 때 → Support Case
       └─ 개발 검토가 필요할 때 → Engineering Issue
```

이 단계적 전환은 불필요한 티켓 증가를 막고, 필요한 문제에는 재현 정보와 고객 영향도를 빠뜨리지 않게 한다.

### Q5. 동일 장애로 여러 문의가 들어오면 어떻게 해야 하는가?

각 문의를 독립적으로 답변하면 조사와 안내가 반복되고, 고객마다 다른 정보를 받을 수 있다. 따라서 상담원은 기존 Incident에 여러 대화를 연결하고 상태 업데이트를 일관되게 전달할 수 있어야 한다.

## 3. 제품 가설과 검증 대상

### 핵심 가설

고객의 대화에 Organization, 제품 환경, 오류 정보, 이력, 서비스 상태를 함께 연결하면, 지원 담당자는 재질문과 맥락 전환을 줄이고 더 빠르고 정확하게 초기 대응할 수 있다.

### 보조 가설

- 구조화된 Technical issue 입력폼은 고객이 문제 해결에 필요한 정보를 더 완결성 있게 제출하도록 돕는다.
- 내부 메모, 팀 멘션, Case 전환은 상담팀에서 기술 전문가로의 인수인계 손실을 줄인다.
- Incident 연결은 동일 장애 관련 문의의 상태 안내를 일관되게 만든다.
- Engineering handoff 화면은 개발팀에 전달할 재현 정보와 고객 영향을 빠뜨리지 않게 한다.

### 1차 프로토타입에서 답해야 할 질문

1. 상담원은 Context Panel만으로 고객에게 다시 물어봐야 할 정보를 빠르게 파악할 수 있는가?
2. Technical issue 입력폼은 자유 채팅만 사용했을 때보다 기술 정보를 충분히 수집하는가?
3. 상담원은 언제 대화를 Case, Incident, Engineering Issue로 전환해야 하는지 이해하는가?
4. 고객은 문의 상태와 장애 진행 상황을 별도 문의 없이 이해할 수 있는가?

## 4. 목표 사용자와 핵심 경험

| 사용자 | 해결하려는 일 | RelayDesk가 제공할 핵심 가치 |
| --- | --- | --- |
| 외부 고객 | 기술 문제를 알리고 진행 상황을 확인한다. | 채팅으로 쉽게 시작하되, 필요한 기술 정보를 빠뜨리지 않고 전달한다. |
| Support Agent | 문의를 분류하고 우선순위를 정해 응답한다. | 고객과 기술 맥락을 한 화면에서 확인하고 담당·상태를 관리한다. |
| Technical Specialist | 복잡한 문제를 조사한다. | 내부 메모, 첨부파일, 재현 정보와 고객 영향을 빠르게 인수받는다. |
| Product·Engineering | 버그와 기능 요청을 검토한다. | 정리된 문제 설명, 환경, 재현 단계, 고객 영향을 가진 개발 이슈를 받는다. |
| CX Manager | 지원 운영의 병목과 반복 문제를 찾는다. | 문의 유형·제품·리전·SLA·해결시간을 분석한다. |

### 대표 목표 상태: EU-West API 오류

1. 고객은 메신저 Home에서 서비스 상태와 도움말을 확인한 뒤 `Contact support`를 선택한다.
2. 고객은 `Technical issue`를 고르고 Public API, Production, EU-West, API v3, 502 오류, 재현 절차와 로그를 제출한다.
3. 운영자 Inbox에는 Enterprise 고객의 고우선순위 문의와 SLA 잔여 시간이 표시된다.
4. 상담원은 상세 화면과 Context Panel에서 고객사, 환경, 최근 배포, 과거 이력, 현재 서비스 상태를 함께 검토한다.
5. 상담원은 내부 메모로 Platform Team을 멘션하고 로그와 Request ID를 공유한다.
6. 같은 원인의 `EU-West API latency` Incident를 찾아 대화를 연결하고, 고객에게 조사 상태를 안내한다.
7. 해결 후 상담원은 해결 내용을 남기고 상태를 `Resolved`로 변경한다.
8. 이 문의는 API·EU-West·502·Enterprise·Incident 연결·해결시간 데이터로 축적된다.

## 5. 1차 프로토타입의 제품 원칙

1. **대화보다 기술 맥락을 우선한다.** 메시지 화면은 항상 고객·조직·환경 정보와 연결된다.
2. **대화를 억지로 티켓화하지 않는다.** 조사와 추적이 필요한 문의만 Case로 승격한다.
3. **고객 메시지와 내부 협업을 분명히 구분한다.** 내부 메모는 고객에게 절대 노출되지 않아야 한다.
4. **상태는 고객과 운영자가 모두 이해할 수 있어야 한다.** 고객은 진행 상황을, 운영자는 업무 상태와 책임자를 확인한다.
5. **통합은 경험을 먼저 검증한다.** Jira·Linear·Slack·SSO 등은 실제 연동 대신 시뮬레이션 UI로 표현한다.

## 6. 성공 기준

실제 운영 데이터가 없는 프로토타입 단계이므로, 아래 기준은 확정 KPI가 아니라 사용성 검증과 데모 평가의 관찰 기준이다.

| 검증 영역 | 성공 신호 |
| --- | --- |
| 문의 정보 완결성 | Technical issue 작성 후 제품, 환경, 오류, 재현 정보, 첨부파일을 확인할 수 있다. |
| 초기 판단 속도 | 상담원이 별도 화면 탐색 없이 고객 영향도와 기술 환경을 설명할 수 있다. |
| 재질문 감소 | 이미 제출된 정보는 Context Panel에 표시되어 같은 질문을 반복하지 않는다. |
| 협업 명확성 | 내부 메모, 멘션, 담당 팀·담당자 변경, 이관 이력이 구분되어 보인다. |
| 전환 이해도 | 대화, Case, Incident, Engineering Issue의 차이와 연결 목적을 사용자가 설명할 수 있다. |
| 고객 투명성 | 고객이 현재 상태, 담당 팀, 예상 답변 시간, Incident 업데이트를 확인할 수 있다. |
| 운영 인사이트 | 고정 샘플 데이터로 문의 유형·제품·리전·SLA·처리량의 관계를 읽을 수 있다. |

## 7. 범위와 비목표

### 반드시 보여 줄 경험

- 고객 메신저 Home, 문의 유형 선택, Technical issue 입력, 고객 대화
- 운영자 Inbox, 상담 상세, Context Panel, 담당자·상태·태그 관리
- 내부 메모와 매크로
- Support Case 전환, Incident 연결, Engineering Issue 연결 시뮬레이션
- Help Center와 기본 Analytics

### 1차 프로토타입의 비목표

- 실시간 WebSocket 채팅, 실제 이메일·외부 메신저·전화 연동
- 실제 Jira, Linear, Slack, SSO, SCIM 연동
- AI 답변·요약·자동 분류·자동 번역
- 실제 결제, 완전한 CRM, 복잡한 워크플로우 빌더
- 운영 데이터를 기반으로 한 고급 리포트

버튼이나 설정 UI는 제공할 수 있으나, 비목표 기능은 안내 Toast 또는 시뮬레이션으로 처리한다.

## 8. 의사결정 기록

- **최우선 검증 가설**: 기술 맥락 기반 해결. 채팅 채널 확대나 자동화보다, 지원 담당자의 문제 이해 품질을 먼저 검증한다.
- **보조 가치**: 지원-개발 연결과 글로벌 비동기 지원은 핵심 가설을 뒷받침하는 경험으로 포함한다.
- **프로토타입 데이터**: 화면과 흐름 검증을 위해 고정된 샘플 데이터를 사용한다.
- **성공의 정의**: 사용자가 RelayDesk를 "채팅 도구"가 아닌 "기술지원 업무를 연결하는 워크스페이스"로 이해하는 상태다.
