# 글로벌 IT 기업용 고객 커뮤니케이션 서비스 기획안

## 1. 기획 배경

### 프로젝트 목표

채널톡과 유사하게 웹사이트 또는 SaaS 제품 안에 설치할 수 있는 고객 채팅 서비스를 만든다.

다만 초기부터 채널톡 전체 기능을 복제하지 않는다. 1차 프로토타입에서는 AI, 전화, 외부 메신저 연동보다 다음 경험을 검증하는 데 집중한다.

> 고객 문의가 단순한 채팅으로 끝나지 않고, 고객 정보·기술 환경·담당자·처리 상태·제품 피드백으로 연결되는가?

### 기본 전제

본 기획안에서 말하는 글로벌 IT 기업은 다음과 같은 기업을 의미한다.

- 글로벌 B2B SaaS 기업
- 개발자 도구 및 API 제공 기업
- 클라우드·보안·데이터 솔루션 기업
- 해외 고객을 보유한 소프트웨어 기업
- 여러 국가와 시간대에서 고객 지원을 운영하는 기업

# 2. 채널톡 서비스 분석

## 2.1 채널톡은 어떤 서비스인가

채널톡은 웹사이트 오른쪽 아래에 표시되는 채팅 위젯으로 알려져 있지만, 실제 제품은 단순 채팅 도구보다 범위가 넓다.

현재 채널톡은 고객 ㅑ상담, 고객정보 관리, 상담 자동화, 사내 협업, 문서 관리, CRM 마케팅, 데이터 분석을 하나의 플랫폼으로 연결하고 있다. 채널톡 측은 이를 고객 상담부터 데이터 분석·마케팅·팀 협업까지 연결하는 비즈니스 운영 플랫폼으로 설명한다.

핵심 구조는 다음과 같다.

```text
고객 접점
    ↓
고객 대화
    ↓
고객정보 확인
    ↓
담당자 배정
    ↓
내부 협업
    ↓
문제 해결
    ↓
상담 데이터 축적
    ↓
운영 개선 및 마케팅 활용

```

즉, 채널톡의 본질은 채팅 UI가 아니라 다음 세 가지를 연결하는 데 있다.

1. 고객과의 대화
2. 고객에 대한 정보
3. 조직 내부의 처리 과정

## 2.2 채널톡의 핵심 기능 구조

### A. 고객 메신저

고객이 웹사이트에서 기업과 대화를 시작하는 접점이다.

주요 기능은 다음과 같다.

- 웹 채팅
- 고객정보 사이드 패널
- 입력폼
- 상담 매크로
- 상담 중 내부대화
- 번역
- 이미지 및 파일 전송
- 상담 카테고리와 태그
- 담당 상담원 배정
- 상담원 상태 관리
- 고객이 사이트를 나간 후 이메일·문자 등으로 답변 알림
- 카카오 상담톡, 네이버 톡톡, 라인, 인스타그램 등의 외부 상담 통합

채널톡은 상담 화면 안에서 고객정보를 확인하고, 여러 외부 채널에서 들어온 상담을 하나의 화면에서 관리하는 구조를 제공한다.

### B. 상담 인박스

고객이 보낸 메시지를 상담원이 처리하는 운영 화면이다.

단순 메시지 목록이 아니라 다음 개념이 포함된다.

- 미배정 상담
- 나에게 배정된 상담
- 처리 중 상담
- 대기 중 상담
- 종료된 상담
- 우선순위
- 담당 팀
- 담당 상담원
- 태그
- 고객정보
- 상담 기록

고객 문의를 메시지가 아닌 처리해야 할 업무 단위로 관리하는 것이 핵심이다.

### C. 팀 메신저

고객과 대화하는 상담 화면과 내부 팀 대화를 연결한다.

채널톡 팀 메신저에서는 그룹 대화방, 비공개 대화방, 다이렉트 메시지, 스레드, 파일 검색 등을 제공하며, 고객 상담과 팀 대화를 오갈 수 있다.

이를 통해 상담원이 고객 문의를 혼자 해결하지 못할 때 개발팀, 운영팀, 물류팀 등과 대화 내용을 공유할 수 있다.

### D. 워크플로우

문의 접수부터 종료까지의 상담 과정을 자동화하는 기능이다.

- 객관식 문의 분류
- 고객 유형별 분기
- 담당 팀 자동 배정
- 상담 태그 자동 설정
- 운영시간 분기
- 상담 만족도 조사
- 반복 상담 프로세스 모듈화
- 노코드 드래그 앤 드롭 편집

채널톡은 고객 등급, 문의 내용, 국가, 운영시간 등에 따라 상담 흐름을 다르게 만들 수 있는 노코드 워크플로우를 제공한다.

### E. 고객정보와 CRM

채팅을 시작한 사용자를 일회성 방문자가 아니라 지속적으로 관리할 고객으로 저장한다.

고객별로 다음 정보를 축적할 수 있다.

- 이름
- 이메일
- 전화번호
- 가입일
- 최근 접속
- 구매 또는 이용 기록
- 상담 이력
- 사용자 속성
- 행동 이벤트
- 고객 세그먼트
- 태그

이 데이터는 상담 개인화와 CRM 메시지 발송에 활용된다.

### F. 도큐먼트와 헬프센터

상담원이 반복적으로 설명하는 내용을 문서로 관리한다.

- 사용 가이드
- FAQ
- 개발자 문서
- 정책 문서
- 버전 히스토리
- 카테고리와 토픽
- 커스텀 도메인
- 다국어 문서
- 웹사이트 형태의 헬프센터

채널톡 도큐먼트는 문서를 내부 지식으로 관리하면서 외부 고객용 웹사이트로도 공개할 수 있고, 다국어·커스텀 도메인·API 커스터마이징을 지원한다.

### G. 상담 통계

상담 결과를 운영 지표로 전환한다.

- 최초 응답시간
- 평균 처리시간
- 상담량
- 상담원별 처리량
- 문의 유입 경로
- 태그별 문의량
- 만족도
- 미처리 상담
- 시간대별 상담량

## 2.3 채널톡이 해결하는 핵심 문제

채널톡은 다음과 같은 기존 고객지원 문제를 해결한다.

### 문제 1. 고객 문의가 여러 채널에 흩어진다

이메일, 웹 채팅, SNS, 전화 등으로 문의가 분산되면 누락 가능성이 높아진다.

채널톡은 여러 상담 채널을 하나의 인박스로 모은다.

### 문제 2. 상담원이 고객 상황을 알지 못한다

고객이 누구인지, 어떤 상품을 이용하는지, 과거에 어떤 문의를 했는지 알 수 없으면 매번 같은 질문을 반복하게 된다.

채널톡은 대화 옆에 고객정보와 상담 이력을 배치한다.

### 문제 3. 문의를 누가 처리하는지 불명확하다

담당자가 정해지지 않으면 중복 답변이나 문의 누락이 발생한다.

채널톡은 담당자, 팀, 상태, 태그로 책임을 명확히 한다.

### 문제 4. 고객의 목소리가 상담팀 안에서만 머문다

제품 문제나 반복 불만이 발생해도 개발팀과 경영진이 이를 알지 못할 수 있다.

채널톡은 고객 상담과 내부 팀 대화를 연결하고, 상담 데이터를 분석 가능한 형태로 축적한다.

# 3. 글로벌 IT 기업 관점의 재해석

## 3.1 채널톡을 그대로 복제하면 안 되는 이유

채널톡의 강점은 커머스와 일반 고객상담에 적합한 폭넓은 기능이다.

하지만 글로벌 IT 기업의 고객 문의는 다음과 같이 성격이 다르다.

```text
일반 고객 문의
“배송은 언제 오나요?”
“환불하고 싶어요.”

IT 제품 문의
“API 요청이 특정 리전에서만 실패합니다.”
“SSO 설정 후 SCIM 동기화가 동작하지 않습니다.”
“v3.2 배포 이후 응답시간이 증가했습니다.”

```

IT 기업의 지원 담당자는 고객 이름만 알아서는 문제를 해결하기 어렵다.

다음과 같은 기술적 맥락이 필요하다.

- 고객이 속한 회사와 워크스페이스
- 사용 중인 요금제
- 제품과 기능
- 제품 버전
- 브라우저와 운영체제
- 클라우드 리전
- Production 또는 Sandbox 환경
- 오류 코드
- 요청 ID
- 로그
- 재현 단계
- 장애 심각도
- 기존 기술지원 이력

따라서 글로벌 IT 기업용 서비스는 고객 메신저보다 **기술지원 컨텍스트 관리**에 더 강해야 한다.

---

## 3.2 글로벌 경쟁 서비스의 공통 구조

Intercom, Zendesk, Front 같은 글로벌 고객지원 제품도 채팅 자체보다 통합 인박스, 티켓, 자동 라우팅, 고객 맥락, 협업, 문서 및 외부 시스템 연결을 중심으로 발전하고 있다.

Intercom은 이메일, 라이브챗, 전화, WhatsApp, SMS, 소셜 메시지를 하나의 인박스에서 처리하고 대화를 티켓으로 전환하며 Salesforce·Slack·Jira 등과 연결하는 구조를 제공한다.

Zendesk 역시 여러 채널의 대화와 고객정보를 하나의 상담원 워크스페이스에 통합하는 것을 핵심으로 한다.

Front는 공유 인박스 안에서 담당자 배정, 내부 코멘트, 자동화, 분석, 외부 도구 연동을 제공하며 여러 부서가 복잡한 고객 요청을 함께 처리하는 데 초점을 둔다.

따라서 새 서비스의 경쟁력은 “또 하나의 채팅 서비스”가 아니라 다음 질문에서 나와야 한다.

> 글로벌 소프트웨어 기업이 고객의 기술 문제를 가장 빠르고 정확하게 이해하고 제품팀까지 전달할 수 있는가?

# 4. 제안 서비스 콘셉트

## 4.1 서비스 정의

### 가칭

**RelayDesk**

이름은 추후 변경할 수 있으며, 현재는 서비스 구조를 설명하기 위한 가칭이다.

### 한 줄 정의

> 글로벌 IT 기업을 위한 고객 대화 기반 기술지원 워크스페이스

### 서비스 설명

RelayDesk는 SaaS 제품이나 웹사이트에 설치되는 고객지원 메신저다.

고객이 채팅으로 문제를 접수하면 서비스가 고객의 계정, 회사, 사용 환경, 제품 버전, 오류 정보와 대화를 하나의 지원 케이스로 구성한다.

상담팀은 해당 케이스를 담당자에게 배정하고 내부 전문가와 협업하며, 필요한 경우 개발 이슈로 전환한다.

---

## 4.2 핵심 차별점

### 1. 대화보다 기술적 맥락을 우선한다

일반 채팅 서비스는 고객 이름과 상담 이력을 보여준다.

RelayDesk는 다음 정보를 함께 보여준다.

- Organization
- Workspace
- Product
- Plan
- Version
- Environment
- Region
- Browser
- OS
- Error code
- Request ID
- Recent deployment
- Current service status

### 2. 대화를 구조화된 지원 케이스로 전환한다

모든 문의를 티켓으로 강제하지는 않는다.

간단한 질문은 대화로 끝낼 수 있고, 조사가 필요한 문제는 지원 케이스로 승격한다.

```text
Conversation
    ↓ 필요 시 승격
Support Case
    ↓ 개발 검토 필요
Engineering Issue

```

### 3. 고객지원과 제품개발의 연결을 강화한다

상담원이 고객 문제를 별도로 정리해 Jira나 Linear에 다시 입력하지 않도록 한다.

프로토타입에서는 실제 연동 대신 다음 전환 경험을 구현한다.

- 대화를 개발 이슈로 전환
- 고객 설명 자동 첨부가 아닌 수동 선택
- 오류 환경과 첨부파일 포함
- 담당 개발팀 선택
- 연결된 이슈 번호 표시
- 이슈 상태를 상담 화면에서 확인

### 4. 글로벌 비동기 지원에 최적화한다

- 고객 현지 시간 표시
- 상담팀 운영시간 표시
- 예상 답변시간 안내
- 국가와 언어 표시
- 시간대를 고려한 SLA
- 대화 재개
- 인수인계 기록

### 5. 장애와 일반 문의를 구분한다

글로벌 IT 서비스에서는 하나의 장애가 여러 고객 문의를 발생시킬 수 있다.

따라서 동일 장애와 관련된 여러 문의를 하나의 Incident에 연결할 수 있어야 한다.

```text
Incident: EU Region API Latency
 ├─ Customer conversation A
 ├─ Customer conversation B
 ├─ Customer conversation C
 └─ Status update

```

# 5. 핵심 사용자

## 5.1 고객 사용자

IT 제품을 사용하는 외부 고객이다.

예시:

- 개발자
- DevOps 엔지니어
- 서비스 관리자
- 보안 담당자
- 제품 운영자
- 기업 구매 담당자

주요 목적:

- 제품 사용법 문의
- 오류 신고
- 계정 및 권한 문의
- 결제 문의
- 장애 확인
- 기능 요청

## 5.2 Support Agent

고객 문의를 최초로 확인하고 해결하는 담당자다.

주요 목적:

- 문의 분류
- 고객정보 확인
- 답변
- 담당자 배정
- 케이스 상태 관리
- 내부 전문가 호출

## 5.3 Technical Specialist

복잡한 기술 문의를 해결하는 담당자다.

예시:

- Solutions Engineer
- Technical Support Engineer
- Implementation Manager
- Security Engineer

## 5.4 Product·Engineering Team

상담 내용을 통해 버그와 기능 요청을 확인한다.

주요 목적:

# 8. 대표 사용자 시나리오

## 시나리오: API 오류 문의

### 1단계. 고객 문의 시작

고객이 SaaS 관리자 화면에서 채팅 버튼을 누른다.

메신저 Home에서 현재 서비스 상태와 주요 문서를 확인한다.

고객은 `Contact support`를 선택한다.

### 2단계. 문의 유형 선택

고객은 `Technical issue`를 선택한다.

### 3단계. 기술정보 입력

서비스가 다음 정보를 입력받는다.

- Product: Public API
- Environment: Production
- Region: EU-West
- Version: API v3
- Error code: 502
- 발생 시각
- 재현 단계
- 로그 파일

로그인한 고객의 Organization과 요금제는 자동으로 표시된 것처럼 구성한다.

### 4단계. 상담 생성

운영자 인박스에 새로운 상담이 생성된다.

```text
Acme Corp
API requests returning 502 in EU-West
Priority: High
Plan: Enterprise
SLA: 42 minutes remaining

```

### 5단계. 상담원 확인

상담원은 오른쪽 Context Panel에서 다음 정보를 확인한다.

- 고객 회사
- Enterprise 플랜
- EU-West 리전 사용
- 과거 유사 문의
- 최근 배포 버전
- 현재 서비스 상태

### 6단계. 내부 협업

상담원은 내부 메모를 작성한다.

```text
@Platform-Team 동일 시간대 EU-West 오류 확인 부탁드립니다.
Request ID와 로그를 첨부했습니다.

```

### 7단계. 장애 연결

담당자는 이미 등록된 `EU-West API latency` Incident를 발견하고 해당 상담을 연결한다.

고객에게는 다음 상태가 표시된다.

```text
현재 EU-West 리전의 API 성능 저하를 조사하고 있습니다.
새로운 정보가 확인되는 대로 이 대화에서 안내해 드리겠습니다.

```

### 8단계. 해결

장애가 해결되면 연결된 모든 상담에 업데이트를 보낸다.

상담원은 해결 내용을 기록하고 상태를 `Resolved`로 변경한다.

### 9단계. 데이터 축적

해당 문의는 다음 분석 데이터에 반영된다.

- API 관련 문의
- EU-West 리전
- 502 오류
- Enterprise 고객
- Incident 연결
- 해결시간

# 15. 최종 제안

이번 프로토타입은 채널톡의 모든 기능을 축소 복제하는 방향으로 만들지 않는다.

채널톡에서 다음 구조만 가져온다.

- 웹 메신저
- 통합 인박스
- 고객정보
- 담당자 배정
- 내부 메모
- 문서
- 상담 통계

그 위에 글로벌 IT 기업에 필요한 다음 구조를 추가한다.

- Organization과 Workspace 중심 고객관리
- 기술환경 정보
- 지원 케이스
- 심각도와 SLA
- Incident 연결
- Engineering Handoff
- 제품·버전·리전별 문의 분석

따라서 제품의 핵심 포지셔닝은 다음과 같다.

> 채널톡처럼 쉽게 대화를 시작하고,  
> IT 서비스데스크처럼 체계적으로 문제를 해결하며,  
> 제품팀이 활용할 수 있는 고객 피드백 데이터까지 남기는 서비스.

1차 프로토타입의 핵심 검증 대상은 AI가 아니다.

**고객의 대화가 기술지원과 제품개선으로 연결되는 경험이 실제로 설득력 있는지 검증하는 것**이 가장 중요한 목표다.

# 16. 소크라틱 검토 및 프로토타입 범위 재정의

## 16.1 무엇을 증명하려는가?

### 질문 1. 고객이 왜 채팅을 시작하기 전에 상태와 문서를 봐야 하는가?

단순한 사용법 질문이나 이미 공지된 장애까지 상담으로 유입되면 고객은 답변을 기다리고, 지원팀은 반복 문의를 처리한다. 따라서 고객 Home은 새 문의 버튼만 강조하지 않고, 현재 서비스 상태와 바로 실행 가능한 도움말을 먼저 보여줘야 한다.

**프로토타입 검증 기준:** 고객이 `Contact support`로 이동하기 전에 서비스 상태와 API 오류 문서를 발견할 수 있어야 한다.

### 질문 2. 기술 정보가 많으면 접수가 어려워지지 않는가?

모든 문의에 기술 폼을 강제하면 일반 문의의 진입 장벽이 높아진다. 반면 기술 장애는 환경·리전·버전·오류 코드가 없으면 지원팀의 첫 답변이 추가 정보 요청으로 끝난다.

**결론:** 문의 유형을 먼저 선택하고, `Technical issue`일 때만 제품·환경·리전·버전·오류 코드·요청 ID를 구조화해 입력한다. 로그인한 고객의 조직 정보는 자동으로 연결된 것으로 표현한다.

### 질문 3. 상담원이 고객 맥락을 한 화면에서 판단할 수 있는가?

대화와 기술 환경이 분리되면 상담원은 여러 화면을 오가거나 고객에게 같은 질문을 반복해야 한다. 따라서 운영자 화면의 핵심은 대화 목록이 아니라 대화·활동·고정 Context Panel을 동시에 보는 구조다.

**프로토타입 검증 기준:** 선택한 대화에서 Organization, 플랜, 워크스페이스, 리전, 버전, 오류 코드, 요청 ID, 최근 활동을 화면 전환 없이 확인한다.

### 질문 4. Incident와 Engineering Issue 연결은 어떤 문제를 해결하는가?

두 연결은 같은 기능이 아니다. Incident는 여러 고객에게 영향을 주는 현재 장애를 공유해 중복 조사와 불확실성을 줄인다. Engineering Issue는 개별 문제의 재현 정보와 고객 영향을 제품팀의 작업 단위로 바꾼다.

**결론:** 프로토타입은 각각을 별도 행동으로 제공하고, 연결 뒤에 식별자·담당 팀·상태가 대화와 Context Panel에 남도록 한다.

### 질문 5. 이번 단계에서 구현하지 않아도 되는 것은 무엇인가?

실제 인증, 저장소, WebSocket, Jira·Linear API, AI, 이메일은 경험 가설을 검증하기 위한 선행 조건이 아니다. 이를 먼저 만들면 검증 속도와 범위 통제가 나빠진다.

**1차 결정:** 시드 데이터와 브라우저 로컬 상태로 API 장애 대표 시나리오를 완결한다. 독립 Customers·Organizations·Analytics 화면은 Context Panel과 요약 정보로 대체한다.

## 16.2 대표 검증 흐름

```text
Customer Home
  → Technical issue 선택
  → API 장애 정보 입력 및 전송
  → 고객 대화에서 처리 상태 확인

Support Inbox
  → Acme Corp 대화 선택
  → 기술 맥락 확인 및 내부 메모 작성
  → Support Case 생성 / Incident 연결 / Engineering Issue 전환
  → 고객에게 상태 업데이트
```

# 17. UI 스타일 상세 명세

## 17.1 디자인 원칙

- **Clear before clever:** 장식보다 정보의 우선순위와 즉시 이해 가능한 문구를 우선한다.
- **Calm and trustworthy:** 밝은 표면과 절제된 블루 포인트로 안정적인 지원 경험을 만든다.
- **Structured information:** 대화, 내부 메모, 기술 정보, 상태를 위치와 라벨로 구분한다.
- **Color carries meaning, not decoration:** 색상은 행동과 상태에만 사용하고, 상태는 아이콘 또는 텍스트와 함께 전달한다.

## 17.2 금지 규칙

- AI·미래지향 이미지를 연상시키는 오로라, 메시, 네온 글로우, 유동형 배경을 사용하지 않는다.
- 그라데이션, 글래스모피즘, 강한 블러, 과도한 그림자, 장식성 3D 그래픽을 사용하지 않는다.
- 한 화면에서 Primary Blue 외의 색을 CTA 용도로 경쟁시키지 않는다.
- 색상만으로 중요도·장애·선택 상태를 전달하지 않는다. 반드시 라벨, 아이콘 또는 텍스트를 병기한다.

## 17.3 토큰


| 용도             | 값         | 사용 규칙                     |
| -------------- | --------- | ------------------------- |
| Primary        | `#3182F6` | 주요 CTA, 활성 탭, 링크, 포커스 링   |
| Primary hover  | `#1B64DA` | hover·pressed 상태          |
| Text           | `#191F28` | 제목 및 기본 본문                |
| Secondary text | `#6B7684` | 메타데이터와 보조 설명              |
| Surface        | `#FFFFFF` | 카드, 입력창, 패널               |
| Canvas         | `#F7F8FA` | 앱 배경, 대화 영역               |
| Divider        | `#E5E8EB` | 패널과 목록 구분                 |
| Success        | `#1F9D55` | 정상 운영, 성공 결과              |
| Warning        | `#D88900` | 대기, 조사 중, SLA 주의          |
| Danger         | `#E5484D` | 장애, High priority, 파괴적 행동 |


- 서체는 Inter 또는 시스템 산세리프를 사용한다. 본문 기본값은 14px/1.45, 메타 정보는 11–12px, 화면 제목은 18–26px 범위로 제한한다.
- 간격은 8px 배수로 구성하고, 카드 모서리는 8–12px, 그림자는 기본적으로 사용하지 않으며 모달에만 약하게 사용한다.
- 버튼은 Primary solid, Neutral outlined, text action 세 유형으로 제한한다. Primary 버튼은 화면의 가장 중요한 행동 하나에만 사용한다.

## 17.4 화면별 적용

### 고객 메신저

- 모바일 우선 단일 열이며, `상태 → 도움말 → 문의 시작` 순으로 배치한다.
- 카드 배경은 흰색, 페이지 배경은 옅은 Gray를 사용한다. 상태 카드는 Green 점과 텍스트를 함께 보여준다.
- 기술 문의 폼은 두 열을 사용할 수 있는 항목만 묶고, 설명이 필요한 항목은 한 열 전체 폭으로 둔다.
- Incident 연결 상태는 옅은 Amber 표면과 `Incident linked` 라벨을 사용한다.

### 운영자 워크스페이스

- 데스크톱 4열 구조: Main navigation, Conversation list, Message detail, Context Panel.
- 선택된 대화는 Blue 좌측 경계와 옅은 Blue 배경으로 표현한다.
- 고객 메시지는 White, 상담원 메시지는 옅은 Blue, 내부 메모는 옅은 Amber와 `Internal note` 라벨로 구분한다.
- 우선순위·상태는 짧은 텍스트 배지로 표시한다. High priority는 Red, 대기는 Amber, 일반 진행 상태는 Blue를 쓴다.
- Context Panel은 스크롤해도 대화 맥락을 유지하며, 고객·조직·기술·연결 작업 순서로 정보를 고정한다.

## 17.5 접근성 및 반응형 기준

- 모든 인터랙션 요소에는 보이는 키보드 포커스를 제공하고, 색 대비는 WCAG AA 수준을 목표로 한다.
- 760px 이하에서는 고객 화면을 우선 제공하며, 운영자 화면은 대화 상세 중심의 단일 열로 축소한다.
- 상태와 에러 메시지는 색상 외에 명확한 텍스트를 사용한다. 아이콘만으로 의미를 전달하지 않는다.
