# RelayDesk Phase 02 구현 핸드오프

## 1. 문서 목적

이 문서는 현재 Inbox 중심으로 구현된 RelayDesk 프론트엔드 프로토타입을 다음 여섯 개 운영 메뉴가 실제로 연결되는 지원 워크스페이스로 확장하기 위한 구현 기준이다.

- 케이스
- 고객
- 조직
- Incident
- 지식
- 분석

Phase 02의 목표는 메뉴별 정적 화면을 늘리는 것이 아니다. 하나의 기술 문의가 Case, Customer, Organization, Incident, Knowledge, Analytics로 이어지는 과정을 사용자가 이해하고 직접 탐색할 수 있어야 한다.

대표 검증 시나리오는 기존의 `EU-West API 502` 문의를 확장한다.

```text
Inbox의 고객 문의
  ↓ 조사 대상으로 승격
Case
  ├─ 누가 영향을 받았는가? → Customer / Organization
  ├─ 공통 장애인가? → Incident
  ├─ 알려진 해결 방법이 있는가? → Knowledge
  └─ 어떤 운영 신호로 남는가? → Analytics
```

## 2. 현재 구현 상태

### 이미 구현된 경험

현재 프로토타입은 빌드 도구 없이 `index.html`, `styles.css`, `app.js`로 구성되어 있다. 모든 상태는 브라우저 메모리에 존재하며 새로고침하면 초기화된다.

고객 화면에서는 다음 흐름이 동작한다.

- 메신저 Home 확인
- 문의 유형 선택
- Technical issue 입력
- 새 대화 생성
- 고객 대화와 Incident 안내 확인

지원 워크스페이스에서는 다음 흐름이 동작한다.

- Inbox의 대화 선택
- 고객 메시지와 내부 메모 확인
- 답장과 내부 메모 작성
- 매크로 문구 사용
- 상태 변경
- 나에게 배정
- Support Case 생성
- Incident 연결
- Engineering Issue 생성 시뮬레이션
- 고객 및 기술 Context 확인

### 현재 구조의 한계

- 좌측 메뉴는 버튼 모양만 있으며 메뉴 전환 상태와 화면이 없다.
- Conversation 안에 고객, 조직, 기술정보, 연결 항목이 혼합되어 있다.
- Customer, Organization, Case, Incident 등이 독립 엔티티가 아니므로 다른 화면에서 일관되게 재사용하기 어렵다.
- 특정 값을 변경해도 연관 화면이나 분석 지표에 반영할 공통 데이터 계층이 없다.
- UI 생성, 상태 변경, 샘플 데이터가 하나의 `app.js`에 모여 있어 메뉴가 추가될수록 수정 범위와 회귀 위험이 커진다.
- 연결된 데이터가 없는 경우, 검색 결과가 없는 경우, 목록 선택 전 상태가 정의되어 있지 않다.

Phase 02에서는 이 제약을 해결하되 백엔드, 영속 저장, 프레임워크 도입까지 범위를 확장하지 않는다.

## 3. 소크라틱 검토와 제품 결정

### Q1. 메뉴가 많아지는 것이 사용자의 문제를 해결하는가?

아니다. 사용자는 메뉴 수가 아니라 지원 업무에 필요한 질문에 답하려고 화면을 이동한다.

- 이 문제는 지금 누가 담당하는가?
- 어떤 고객과 조직이 영향을 받았는가?
- 동일한 문제가 다른 고객에게도 발생했는가?
- 이미 알려진 해결 방법이 있는가?
- 이 문제는 SLA와 지원 운영에 어떤 영향을 주었는가?

따라서 모든 메뉴는 독립된 데이터 섬이 아니라 위 질문 사이를 이동하는 연결 지점이어야 한다.

### Q2. Conversation과 Case는 왜 분리해야 하는가?

Conversation은 고객과 주고받는 대화이고, Case는 조사·책임·SLA·해결 결과를 추적하는 업무 단위다. 모든 대화를 Case로 만들면 간단한 질문까지 운영 업무로 과도하게 확대된다. 반대로 복잡한 문의를 대화로만 관리하면 담당자, 심각도, 조사 결과와 해결 기록을 안정적으로 추적할 수 없다.

따라서 다음 원칙을 적용한다.

- 간단한 문의는 Conversation에서 해결한다.
- 조사, 팀 협업, 장기 추적이 필요할 때 Case로 전환한다.
- 하나의 Case는 원본 Conversation을 참조한다.
- Phase 02에서는 하나의 Conversation에 최대 하나의 Case를 연결한다.

### Q3. Customer와 Organization을 왜 따로 관리하는가?

글로벌 B2B SaaS 지원에서는 문의자는 개인이지만 영향 범위와 계약 관계는 조직 단위다. 같은 사용자의 문제라도 Enterprise Production 환경과 Free Sandbox 환경은 다른 우선순위와 대응이 필요하다.

따라서 다음을 구분한다.

- Customer는 사람, 연락 정보, 언어, 시간대, 최근 활동을 나타낸다.
- Organization은 회사, 플랜, 계약 등급, 제품, 워크스페이스, 다수 고객과 지원 영향을 나타낸다.
- Customer는 하나의 Organization에 속한다.
- Conversation과 Case는 Customer와 Organization을 모두 참조한다.

### Q4. Incident는 Case의 상태 중 하나인가?

아니다. Case는 개별 고객 문제이고 Incident는 여러 고객과 조직에 영향을 줄 수 있는 공통 운영 사건이다. 둘을 같은 상태로 취급하면 장애 하나에 연결된 고객 영향과 업데이트를 집계할 수 없다.

따라서 Incident를 독립 엔티티로 관리한다.

- 하나의 Incident는 여러 Case와 Conversation을 연결할 수 있다.
- Case는 Phase 02에서 최대 하나의 Incident에 연결한다.
- Incident 상태 변경은 연결된 고객 대화의 Incident 배너와 관련 상세 화면에 반영한다.
- Incident 해결이 Case를 자동으로 해결하지는 않는다. 상담원이 고객별 확인 후 Case를 해결한다.

### Q5. Knowledge는 문서 보관함인가?

아니다. 지원 업무 중 적절한 문서를 찾고 고객 답변에 재사용할 수 없다면 별도 메뉴의 가치가 낮다.

따라서 Knowledge는 다음 두 흐름을 모두 지원한다.

- 운영자가 문서를 검색·분류·수정한다.
- Inbox에서 답장을 작성할 때 관련 문서를 선택해 링크 문구를 삽입한다.

실제 공개 URL이나 Help Center 배포는 만들지 않고 샘플 문서 URL을 사용한다.

### Q6. Analytics는 고정된 장식용 차트여도 되는가?

Phase 01에서는 가능했지만, Phase 02의 목적에는 부족하다. 상태와 연결을 변경했을 때 최소한 건수형 지표는 공통 데이터에서 다시 계산되어야 워크스페이스가 하나의 시스템처럼 느껴진다.

따라서 다음 기준을 적용한다.

- 열린 Case 수, 상태별 Case 수, Incident 연결 수, 제품·리전·유형별 건수는 현재 공용 데이터에서 계산한다.
- 평균 응답시간처럼 충분한 원천 데이터가 없는 값은 명시된 샘플 지표로 표시한다.
- 계산 지표와 샘플 지표를 코드와 화면 문구에서 구분한다.

### Q7. 현재 단일 파일 구조를 유지해야 하는가?

현재 기능 규모에서는 가능하지만 여섯 메뉴와 공용 관계를 추가하면 수정하기 어려워진다. Phase 02에서는 프레임워크나 빌드 도구를 새로 도입하지 않고 브라우저 표준 ES modules로 책임을 분리한다.

결정:

- Vanilla JavaScript를 유지한다.
- `index.html`에서 module entry를 불러온다.
- 샘플 데이터, 상태와 변경 작업, 공통 UI, 메뉴별 화면을 분리한다.
- 외부 라이브러리는 추가하지 않는다.

## 4. Phase 02 목표와 완료 조건

### 한 문장 목표

> 지원 담당자가 Inbox에서 시작한 기술 문제를 Case, 고객, 조직, Incident, 지식, 분석 화면으로 자연스럽게 추적하고, 한 화면에서 수행한 변경이 관련 화면에 일관되게 반영되는 상호연결형 프로토타입을 완성한다.

### 완료 조건

다음 조건이 모두 충족되어야 Phase 02가 완료된 것으로 본다.

1. 좌측 여섯 메뉴가 모두 동작하며 선택한 메뉴가 명확하게 표시된다.
2. 각 메뉴에 최소 하나의 완성된 목록 또는 대시보드 화면과 관련 상세 화면이 있다.
3. Customer, Organization, Case, Incident, Article 데이터가 ID 관계로 연결된다.
4. 목록에서 선택한 항목의 상세를 확인하고 연관 엔티티로 이동할 수 있다.
5. Case와 Incident의 핵심 변경이 Inbox와 다른 관련 화면에 즉시 반영된다.
6. Knowledge 문서를 Inbox 답장에 삽입할 수 있다.
7. Analytics의 건수형 지표가 현재 데이터 상태에서 계산된다.
8. 기존 고객 문의와 Inbox 데모 흐름이 계속 동작한다.

## 5. 정보 구조와 공통 화면 원칙

### 좌측 내비게이션

지원 워크스페이스의 메뉴 순서는 다음으로 고정한다.

1. 인박스
2. 케이스
3. 고객
4. 조직
5. Incident
6. 지식
7. 분석

메뉴 버튼은 다음 규칙을 따른다.

- 현재 메뉴는 색상과 배경으로 활성 상태를 표시한다.
- 메뉴 전환 시 이전 메뉴의 선택 항목은 상태에 유지해 돌아왔을 때 같은 상세를 볼 수 있게 한다.
- 고객 화면으로 전환했다가 지원 워크스페이스로 돌아와도 마지막 운영 메뉴를 유지한다.
- URL 라우팅과 브라우저 뒤로 가기 연동은 Phase 02 범위에서 제외한다.

### 메뉴별 기본 레이아웃

목록과 상세가 있는 메뉴는 기존 Inbox의 화면 문법을 재사용한다.

```text
┌──────────┬────────────────────────┬────────────────────────────────────┐
│ Main Nav │ Search / Filter / List │ Selected Entity Detail             │
└──────────┴────────────────────────┴────────────────────────────────────┘
```

Analytics는 목록 없이 넓은 대시보드 영역을 사용한다.

### 공통 상호작용

- 검색은 대소문자를 구분하지 않는 부분 일치로 동작한다.
- 필터는 여러 종류를 함께 적용할 수 있다.
- 검색과 필터 결과 수를 목록 상단에 표시한다.
- 선택된 항목이 필터 결과에서 제외되면 첫 번째 결과를 선택한다.
- 결과가 없으면 필터 초기화 버튼이 포함된 빈 상태를 표시한다.
- 연결 데이터가 없으면 빈 영역을 숨기지 않고 “연결된 항목이 없습니다”라고 표시한다.
- 파괴적 삭제는 구현하지 않는다.
- 성공한 변경은 화면 반영과 짧은 Toast로 확인한다.


### 공용 변경 작업

화면이 데이터를 직접 변경하지 않고 다음 성격의 작업 함수를 호출한다.

- `selectAgentMenu(menu)`
- `navigateToEntity(type, id)`
- `updateCase(caseId, patch)`
- `createCaseFromConversation(conversationId)`
- `linkCaseToIncident(caseId, incidentId)`
- `unlinkCaseFromIncident(caseId)`
- `addIncidentUpdate(incidentId, update)`
- `updateIncidentStatus(incidentId, status)`
- `updateArticle(articleId, patch)`
- `insertArticleIntoReply(articleId)`

실제 함수 이름은 구현 중 조정할 수 있으나, 화면 렌더링과 데이터 변경 책임은 분리해야 한다.

### 관계 변경 전파 규칙

#### Case 생성

- 새 Case는 원본 Conversation의 Customer, Organization, 기술정보를 참조한다.
- Conversation의 `caseId`를 새 Case ID로 갱신한다.
- Inbox 상세와 Cases 목록에 즉시 표시한다.
- 같은 Conversation에서 다시 생성하려 하면 기존 Case 상세로 이동한다.

#### Case 상태 변경

- Case 상태는 Case 목록과 상세에 즉시 반영한다.
- Conversation 상태는 자동으로 동일하게 덮어쓰지 않는다.
- Case가 Resolved가 되면 Inbox Context에 해결 상태를 표시하지만 고객 대화 종료는 별도 상태 변경으로 남긴다.

#### Incident 연결

- Case의 `incidentId`와 원본 Conversation의 `incidentId`를 같은 값으로 갱신한다.
- Inbox 고객 대화, Case 상세, Incident 상세의 연결 수에 즉시 반영한다.
- 다른 Incident로 변경하면 이전 Incident 집계에서 제거하고 새 Incident 집계에 포함한다.

#### Incident 업데이트

- Incident 타임라인에 새 업데이트를 추가한다.
- 연결된 고객 대화에는 최신 공개 업데이트 문구를 Incident 배너로 표시한다.
- Phase 02에서는 내부/외부 업데이트 가시성 구분을 추가하지 않고 모든 Incident 업데이트를 고객에게 보여 주는 샘플 공개 업데이트로 취급한다.

#### Incident 해결

- Incident 상태와 해결 시각을 갱신한다.
- 연결된 고객 대화의 배너를 해결 상태로 변경한다.
- Case와 Conversation은 자동으로 Resolved 처리하지 않는다.

#### Knowledge 삽입

- Inbox에서 Public 문서만 고객 답장에 삽입할 수 있다.
- Internal 또는 Draft 문서는 검색 결과에 표시할 수 있지만 삽입 버튼은 비활성화하고 이유를 표시한다.
- 삽입 시 답장 작성기에 `문서 제목 + 샘플 URL` 문구를 추가한다.

8. Knowledge에서 `API 5xx troubleshooting` 문서를 찾아 고객 답장에 삽입한다.
9. Incident를 `Resolved`로 변경한다.
10. Analytics에서 진행 중 Incident 수와 Incident 상태 분포가 갱신된 것을 확인한다.

### 시나리오 B. 고객 이력에서 반복 문제 발견

## 10. 구현 구조

Phase 02는 다음 책임 단위로 분리한다. 실제 파일명은 이 구조를 유지하는 범위에서 조정할 수 있다.

```text
index.html
styles.css
src/
├─ app.js
├─ data.js
├─ state.js
├─ actions.js
├─ utils.js
└─ views/
   ├─ shell.js
   ├─ inbox.js
   ├─ cases.js
   ├─ customers.js
   ├─ organizations.js
   ├─ incidents.js
   ├─ knowledge.js
   ├─ analytics.js
   └─ customer.js
```

### 모듈 책임

- `data.js`: 정규화된 샘플 데이터와 고정 기준 시각
- `state.js`: UI 상태, 상태 조회와 갱신
- `actions.js`: 엔티티 변경과 관계 전파
- `utils.js`: 검색, 필터, 날짜, 상태 라벨, HTML escape 등의 공통 함수
- `views/shell.js`: 상단바, 좌측 내비게이션, Toast, Modal
- 메뉴별 view: 해당 화면의 렌더링과 이벤트 식별자 제공
- `app.js`: 초기화, 이벤트 위임, 전체 렌더 조정

### 렌더링 규칙

- 기존처럼 상태 변경 후 필요한 화면 전체를 다시 렌더링하는 방식을 유지한다.
- 메뉴별 view는 HTML 문자열을 반환하되 데이터 원본을 직접 수정하지 않는다.
- 이벤트는 인라인 `onclick` 전역 함수 대신 `data-action`, `data-id` 기반 이벤트 위임으로 이동한다.
- 사용자 입력을 HTML에 표시할 때 escape 처리한다.

### 스타일 구조

기존 색상, badge, card, field, modal, toast를 재사용한다. 추가 스타일은 다음 영역으로 구분한다.

- 공통 워크스페이스 레이아웃
- 목록/필터
- 엔티티 상세
- 상태 및 관계 카드
- Knowledge 편집
- Analytics 카드와 분포
- 빈 상태

지원 워크스페이스는 데스크톱 프로토타입을 우선한다. 작은 화면에서는 기존처럼 고객 화면 사용성을 보존하고 운영 메뉴 전체의 모바일 최적화는 Phase 02 완료 조건에서 제외한다.

## 11. 구현 순서

### Step 1. 회귀 기준 확보

- 현재 고객 문의 제출과 Inbox 주요 동작을 수동 검증한다.
- 기존 샘플 시나리오와 화면 상태를 체크리스트로 기록한다.

### Step 2. 데이터 정규화

- Conversation에 중복된 고객, 조직, Case, Incident 정보를 독립 컬렉션으로 이동한다.
- 기존 화면이 새 ID 관계로 동일한 내용을 표시하도록 전환한다.
- 이 단계에서는 사용자에게 보이는 기능을 추가하지 않는다.

### Step 3. 모듈화와 공통 내비게이션

- ES modules 구조로 분리한다.
- 이벤트 위임과 공용 action 계층을 도입한다.
- 활성 메뉴와 메뉴 전환을 구현한다.
- 기존 고객 화면과 Inbox의 회귀를 다시 확인한다.

### Step 4. 핵심 관계 메뉴

다음 순서로 구현한다.

1. Cases
2. Customers
3. Organizations
4. Incidents

Cases를 먼저 구현해 Conversation에서 시작한 관계를 기준점으로 삼는다. Customers와 Organizations를 연결한 뒤, 다대일 장애 관계를 Incidents에 추가한다.

### Step 5. Knowledge 연결

- 문서 목록, 상세, 편집을 구현한다.
- Inbox 작성기에서 문서 선택과 삽입을 연결한다.

### Step 6. Analytics 계산

- 공용 데이터 기반 selector를 작성한다.
- Overview, Issue Insights, Team Performance, SLA를 구현한다.
- 상태 변경 이후 지표 재계산을 확인한다.

### Step 7. 빈 상태와 통합 검증

- 검색 결과 없음, 연결 없음, 선택 없음 상태를 추가한다.
- 대표 시나리오를 처음부터 끝까지 실행한다.
- 시각적 일관성과 기존 기능 회귀를 확인한다.

## 12. 테스트 및 인수 기준

자동 테스트 환경은 새로 도입하지 않는다. 브라우저 기반 수동 시나리오와 정적 검사를 수행한다.

### 공통 내비게이션

- 모든 메뉴 버튼이 대응 화면을 연다.
- 활성 메뉴 표시가 정확하다.
- 메뉴를 왕복해도 마지막 선택 항목이 유지된다.
- 고객 화면 전환 후 돌아와도 마지막 운영 메뉴가 유지된다.

### Cases

- 검색과 각 필터가 함께 적용된다.
- Case 상세에서 연결된 엔티티로 이동할 수 있다.
- 상태, 심각도, 담당자 변경이 목록과 상세에 반영된다.
- Inbox에서 생성한 Case가 Cases 목록에 나타난다.
- 이미 Case가 있는 Conversation에서는 중복 생성되지 않는다.

### Customers와 Organizations

- 고객 검색과 Organization 필터가 동작한다.
- 고객 상세의 대화·Case 수가 실제 관계와 일치한다.
- 조직 상세의 고객, 열린 Case, Incident 영향 정보가 일치한다.
- Customer, Organization, Case 사이를 교차 이동할 수 있다.

### Incidents

- 새 Incident를 생성할 수 있다.
- Case 연결과 해제가 양쪽 상세 및 Inbox에 반영된다.
- 상태 업데이트가 Incident 타임라인과 고객 대화 배너에 반영된다.
- Incident 해결 시 연결된 Case가 자동 해결되지 않는다.
- 연결된 고객과 조직 수가 중복 없이 계산된다.

### Knowledge

- 검색과 필터가 함께 동작한다.
- 문서를 생성하고 수정할 수 있다.
- Public 문서를 Inbox 답장에 삽입할 수 있다.
- Internal과 Draft 문서는 고객 답장에 삽입할 수 없다.

### Analytics

- 현재 데이터에서 계산된 건수가 메뉴별 실제 목록과 일치한다.
- Case와 Incident 상태를 변경하면 관련 지표가 갱신된다.
- 날짜와 제품 필터가 모든 탭에 동일하게 적용된다.
- 데이터가 없는 조건에서 차트 대신 빈 상태가 표시된다.

### 기존 기능 회귀

- 고객이 Technical issue를 제출할 수 있다.
- 새 Conversation이 Inbox에 나타난다.
- 상담원 답장과 내부 메모가 구분되어 표시된다.
- 매크로, 상태 변경, 나에게 배정이 동작한다.
- 고객에게 내부 메모가 노출되지 않는다.
- Case, Incident, Engineering Issue 연결 모달이 계속 동작한다.

### 정적·시각 검증

- 브라우저 콘솔 오류가 없다.
- ES module 경로와 정적 서버 실행이 정상이다.
- HTML에 사용자 입력을 삽입할 때 escape가 적용된다.
- 1060px 이상에서 목록과 상세이 잘리지 않는다.
- 고객 화면은 기존 모바일 레이아웃을 유지한다.

## 13. 범위에서 제외하는 항목

- 백엔드와 데이터베이스
- 새로고침 이후 상태 유지
- URL 라우팅과 브라우저 히스토리
- 로그인, 실제 SSO, 역할별 권한
- 실시간 채팅과 WebSocket
- 실제 Jira, Linear, Slack 연동
- AI 답변, 요약, 분류, 문서 추천
- 실제 Help Center 배포와 문서 공개 URL 생성
- CSV 내보내기와 고급 분석 리포트
- 엔티티 삭제와 복구
- 운영 워크스페이스 전체의 모바일 최적화

제외 기능의 버튼이 필요한 경우 실제 성공처럼 오해시키지 않고 “프로토타입에서는 지원하지 않습니다”라는 안내를 표시한다.

## 14. 최종 구현 판단 기준

Phase 02의 성공은 화면 수로 평가하지 않는다. 다음 질문에 “예”라고 답할 수 있어야 한다.

> 지원 담당자가 하나의 고객 대화에서 시작해, 문제의 책임과 상태를 Case로 관리하고, 영향을 받는 고객과 조직을 확인하며, 공통 Incident와 해결 문서를 연결하고, 그 결과가 운영 지표에 반영되는 전체 과정을 막힘없이 이해할 수 있는가?

이 질문에 답하지 못하는 기능은 메뉴에 포함되어 있더라도 Phase 02의 핵심 완료로 보지 않는다.
